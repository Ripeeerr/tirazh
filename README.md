# Тираж

Демонстрационное веб-приложение онлайн-типографии: каталог продукции, расчёт стоимости, интерактивный предпросмотр макета и работа с заказами. Есть кабинеты клиента и менеджера. Проект создан для портфолио; типография вымышленная, реальные заказы и платежи не принимаются.

![Полиграфия «Тираж»](frontend/public/images/night-studio/hero.webp)

## Возможности

- Визитки, листовки, буклеты, открытки, постеры и приглашения.
- Выбор формата, бумаги, сторон печати и количества; серверный расчёт стоимости со скидкой за объём.
- Загрузка PDF, PNG и JPEG до 10 МБ. Предпросмотр изображения или первой страницы PDF.
- Масштаб от 1× до 6×, перетаскивание, управление мышью, касаниями, клавиатурой и текстовыми кнопками.
- Регистрация при оформлении с сохранением выбранных параметров.
- История заказов, комментарии, версии макетов и запросы исправлений.
- Кабинет менеджера: фильтрация заказов, переходы статусов и добавление продукции в каталог.
- Адаптивный интерфейс в постоянном тёмном оформлении «Ночная студия».

Один заказ содержит один вид продукции. Получение и оплата представлены демонстрационным сценарием самовывоза. После обновления страницы параметры заказа сохраняются, локальный файл нужно выбрать заново.

## Запуск

Нужны Docker и Docker Compose. В корне проекта создайте `.env`:

```bash
cp .env.example .env
```

Замените `POSTGRES_PASSWORD` собственным длинным паролем из URL-безопасных символов. Для готовой сборки с Nginx:

```bash
docker compose -f compose.production.yaml up --build -d
```

Приложение: **http://localhost:8080**. Документация API: **http://localhost:8080/api/docs**.

Миграции применяются перед стартом API, каталог заполняется автоматически. Клиент регистрируется через интерфейс. Чтобы создать менеджера:

```bash
docker compose -f compose.production.yaml exec api uv run --no-sync python -m app.seed --manager your-email@example.com
```

Пароль вводится интерактивно. Команда не повышает права уже существующего пользователя.

Просмотр логов и остановка:

```bash
docker compose -f compose.production.yaml logs -f api web
docker compose -f compose.production.yaml down
```

База и макеты сохраняются в именованных томах. Флаг `down -v` удаляет эти данные. PostgreSQL доступен только локально через `127.0.0.1:5432`; API не публикует отдельный порт.

После изменения фронтенда пересоберите web:

```bash
docker compose -f compose.production.yaml up --build -d web
```

Если Docker сообщает `network ... not found`, пересоздайте контейнеры и сеть без удаления томов:

```bash
docker compose -f compose.production.yaml down --remove-orphans
docker compose -f compose.production.yaml up -d --force-recreate
```

## Разработка

Обычный Compose запускает Vite через Bun и API через uv с автоматической перезагрузкой. Зависимости и кэши находятся в отдельных томах; изменение исходников не требует пересборки. Первый запуск скачивает зависимости из сети.

Перед переключением остановите production-конфигурацию:

```bash
docker compose -f compose.production.yaml down
docker compose up --build -d --remove-orphans
```

Адрес приложения остаётся **http://localhost:8080**. Не запускайте обе конфигурации одновременно: они используют одинаковые порты и тома.

Для запуска без Docker подготовьте PostgreSQL и `backend/.env` по примеру `backend/.env.example`. `DATABASE_URL` обязателен; встроенного пароля БД нет.

```bash
cd backend
uv sync --frozen
uv run alembic upgrade head
uv run python -m app.seed
uv run uvicorn app.main:app --reload
```

В другом терминале:

```bash
cd frontend
bun install --frozen-lockfile
bun run dev
```

Адрес: **http://localhost:5173**. Vite проксирует `/api` на порт 8000. Нужны Bun 1.4.4, uv и Node.js 22 для совместимости Vite/esbuild. Управление зависимостями и запуск команд фронтенда выполняются через Bun, Python — через uv. Версии зависимостей зафиксированы в lock-файлах.

## Проверки

```bash
cd backend
uv run ruff check app migrations tests
uv run ruff format --check app migrations tests
uv run pytest -q
```

API-тесты по умолчанию используют SQLite в памяти. Для PostgreSQL задайте `TEST_DATABASE_URL`, указывающий на отдельную БД `tirazh_test`: её содержимое очищается тестовой фикстурой.

```bash
cd frontend
bun run test:unit
bun run format:check
bun run build
bunx playwright install chromium
bun run test:e2e
```

Playwright поднимает отдельные API и Vite. Тестовый менеджер с заранее известным паролем создаётся только в выделенной E2E-базе, а не в рабочем приложении. Для E2E с PostgreSQL используйте `E2E_DATABASE_URL` с именем БД `tirazh_e2e`.

Типы API генерируются из OpenAPI. После изменения схем при запущенном API:

```bash
cd frontend
bun run api:types
```

В GitHub Actions настроены проверки API на PostgreSQL, миграций, фронтенда и E2E.

## Безопасность

- Пользовательские тексты отображаются через JSX; сырые HTML-вставки не используются. Адрес возврата после входа ограничен внутренними URL.
- Пароли хешируются через scrypt. Случайные сессионные токены передаются в HttpOnly/SameSite-cookie; в БД хранится их хеш.
- Заказы и файлы проверяются на принадлежность пользователю, менеджерские методы требуют соответствующей роли. Стоимость и допустимые переходы статусов определяются сервером.
- Источник изменяющих запросов проверяется по `FRONTEND_ORIGIN`, а не по присланному `Host`.
- Загружаемые файлы ограничены по размеру, расширению и сигнатуре. Они хранятся под случайными идентификаторами, выдаются как приватные вложения с `nosniff` и CSP sandbox.
- Nginx задаёт CSP и ограничения частоты запросов авторизации и загрузки файлов. Пользовательские макеты обрабатываются внутри приложения и не передаются сторонним сервисам.
- Утилиты тестирования проверяют разобранное имя PostgreSQL-базы перед очисткой данных или созданием E2E-менеджера; параметры URL не позволяют обойти эту проверку.
- `.env`, ключи, базы и резервные копии исключены из Git. `.env.*` также исключены из Docker-контекстов. В примерах и тестах используются только демонстрационные значения.

Перед размещением в интернете настройте HTTPS, `SECURE_COOKIES=true` и точный `FRONTEND_ORIGIN` без завершающего слеша. Режим Vite предназначен для разработки, публичное размещение — через production-конфигурацию.

Перед развёртыванием выполните проверки из раздела выше и проверьте зависимости командой `bun audit` в каталоге `frontend`.

## Структура

```text
backend/app/core/           настройки, пароли и сессии
backend/app/db/             модели и подключение к БД
backend/app/modules/        API и бизнес-логика
backend/migrations/         миграции схемы
backend/tests/              проверки API и безопасности
frontend/src/app/           маршруты и провайдеры
frontend/src/pages/         страницы приложения
frontend/src/components/    общие компоненты
frontend/src/features/      пользовательские сценарии
frontend/src/api/           HTTP-клиент и типы API
frontend/tests/             unit- и E2E-тесты
```

`develop` содержит текущую разработку, `main` предназначена для проверенных релизов. Изменения ведутся в отдельных ветках и объединяются merge-коммитами. Сообщения коммитов — на русском с префиксами Conventional Commits.
